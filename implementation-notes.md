# Implementation notes

One line per non-obvious decision: what, why, alternative rejected.
Grep-friendly. `DEVIATION:` marks a departure from the spec.

## Gate 0 — 2026-10-09

- 2026-10-09 Scaffolded from `duckdb/extension-template-rs@8ec303e` rather than hand-writing the C-API glue; the template is the only thing community CI is known to build. Rejected: writing `duckdb_extension.h` bindings by hand.
- 2026-10-09 `extension-ci-tools` vendored as a git submodule pinned to tag `v1.5.6` (`3fd6109f`), matching `TARGET_DUCKDB_VERSION`. Rejected: copying the makefiles in, which would silently drift from upstream.
- 2026-10-09 OQ2 (WASM) resolved by actually building all three WASM platforms locally, not by reading CI YAML. `make wasm_mvp`, `make wasm_eh`, `make wasm_threads` all produce artifacts. See ADR-0002.
- 2026-10-09 WASM artifact is 184,531 B raw / 64,497 B gzipped with `cdshealpix` + `duckdb-rs` already linked in. Gate 5 budget is 2 MB gzipped, so the dependency floor costs ~3% of budget. Recorded as a baseline to watch as `moc` is added in Gate 2.
- 2026-10-09 `DEVIATION:` Cargo `edition = "2021"` per AGENTS.md Stack, while the upstream template uses `edition = "2024"`. 2021 compiles clean against `duckdb ~1.10506.0`; kept the spec's value. Revisit only if a dependency forces 2024.
- 2026-10-09 `DEVIATION:` README Prerequisites says DuckDB "1.4.x"; the template, ci-tools and the `duckdb` crate all target **v1.5.6**, so the pin is v1.5.6. Chose the conservative option (follow the toolchain that actually builds) and logged it rather than stopping. README needs a one-word correction — flagged for the maintainer, not edited, because README is the spec. See ADR-0003.
- 2026-10-09 `USE_UNSTABLE_C_API=1` is not a choice: `duckdb-rs` requires unstable C API surface, so artifacts are stamped `C_STRUCT_UNSTABLE` and load only on the exact DuckDB version. Verified by observing the local v1.5.5 CLI refuse a v1.5.6 build. See ADR-0003.
- 2026-10-09 `src/lib.rs` declares submodules as `#[path = "pixel.rs"] mod pixel;`. Load-bearing: `src/wasm_lib.rs` does `mod lib;` for the staticlib target, which would otherwise make Rust look for `src/lib/pixel.rs`. A bare `mod pixel;` breaks WASM while native keeps working — a silent, gate-5-late failure. Every future module must use the same form.
- 2026-10-09 `make test` extended to run `cargo test` and to depend on `debug`, because README defines `make test` as "cargo test (unit + proptest) + sqllogictest" and a clean checkout otherwise fails with "Extension not found" before building.
- 2026-10-09 Null handling in `ang2pix_chunk` is two passes (write values, then apply the null mask) specifically to avoid allocating a scratch `Vec` per chunk; `as_mut_slice` borrows mutably and conflicts with `set_null`. Rejected: per-chunk `Vec<i64>`, which violates the no-allocation-in-hot-loops constraint.
- 2026-10-09 Strict RA/Dec validation is always on in Gate 0. The `healpix_strict_input=false` lenient path (normalise RA, clamp Dec) is NOT implemented — it needs a DuckDB setting read, which is extra FFI surface not justified by one function. ASSUMPTION: deferring it to Gate 1 is safe because `true` is the documented default, so Gate 0 behaviour already matches the contract for every default-configured user.
- 2026-10-09 `ureq` appears in the dependency tree but is a **build-dependency of `libduckdb-sys`** (fetches headers at build time). Confirmed it does not link into the extension: `cargo tree -i ureq -e normal` reports nothing, and `nm -gU target/debug/libhealpix.dylib | grep -ciE 'ureq|rustls|socket'` returns 0. Invariant 2 (no network inside the extension) holds.
- 2026-10-09 The unit-test oracle table in `src/pixel.rs` was NOT written from my own output. A hand-guessed assertion about equatorial base cells failed; rather than adjust the test to match the code, the 12 expected values were generated independently by `astropy-healpix` and agree with `cdshealpix` on every row. Circular tests prove nothing (invariant 4 in spirit).
- 2026-10-09 `docs/functions.md` is generated by `tools/gen_functions_doc.py` from `function_descriptions.csv`; the script fails loudly if any function lacks a description or example, which is a README acceptance criterion.
- 2026-10-09 `duckdb-rs` already contains panics in `contain_callback` (callback.rs:28-43, "never unwind to the caller"). Our explicit `catch_unwind` is a second INNER layer, kept so invariant 7 is auditable here rather than hostage to a dependency's internals. Rejected: dropping ours — in WASM the failure mode is a dead browser tab.
- 2026-10-09 `DEVIATION:` README says a caught panic surfaces as `InternalException`. Not reachable: the C Extension API's only error channel is `duckdb_scalar_function_set_error(info, msg)`, which DuckDB always raises as Invalid Input Error. Internal vs user error is distinguished by MESSAGE (`healpix: internal error (...)`), not class. See ADR-0005. README needs a correction — flagged, not edited.
- 2026-10-09 Output written via `as_mut_slice_with_len::<i64>(len)`, not `as_mut_slice::<i64>()`. The latter returns `capacity()` (2048) elements, wider than the live rows; both are in-bounds for `i < len` but the narrower method makes the SAFETY obligation match reality. Found in review.
- 2026-10-09 Mid-chunk error leaves earlier rows written and the null mask unapplied. Safe: DuckDB discards the output chunk of a scalar function that reported an error, so partial values are unobservable. Now covered by explicit `statement error` cases over 3000-row ranges in `test/sql/pixel.test`, not just ad-hoc checks.
- 2026-10-09 Test suite proven non-vacuous by mutation: injecting `depth-1` into `ang2pix` fails BOTH `cargo test` (oracle table) and sqllogictest (`pixel.test:15`). Done because a reviewer alleged an always-false WHERE clause; the vacuous self-comparison it referred to had already been removed, and mutation is the only real proof a test can fail.

## Gate 0 — post-review corrections, 2026-10-09

- 2026-10-09 `DEVIATION: corrected an earlier wrong call.` I initially dismissed a reviewer's "CanThrow()/error-mode" concern as fabricated because `grep` found no such symbol in duckdb-rs or libduckdb-sys. The absence IS the problem, not its refutation: the C API has no `duckdb_scalar_function_set_error_mode`, so the function is declared CANNOT_ERROR while it throws. The concern was real and is now ADR-0006.
- 2026-10-09 ADR-0006: strict validation can reject a query whose result rows are ALL valid. Reproduced with an explicit DOUBLE dictionary vector through a hash join — 3000 rows, one distinct `ra = 10.0`, zero rows with `ra = 400.0`, yet the query errors on 400. Control with both dictionary entries legal returns 3000. Pinned by a `statement error` case plus a passing control in `test/sql/pixel.test`. Parquet `PLAIN_DICTIONARY` did not reproduce it; the hash join did.
- 2026-10-09 Consequence of ADR-0006: `healpix_strict_input=false` is promoted from deferred convenience to a REQUIRED Gate 1 deliverable, because turning strict off removes the throw and makes the forced CANNOT_ERROR declaration honest.
- 2026-10-09 `DEVIATION: corrected my own SAFETY comment.` It claimed `flat_vector()` "normalises the argument to the FLAT representation". False. `DataChunkHandle::flat_vector` is only `FlatVector::from_raw(duckdb_data_chunk_get_vector(..))` — stores a pointer plus `duckdb_vector_size()` capacity, inspects nothing; no `Flatten` call exists anywhere in duckdb-rs. The real guarantee is `input.Flatten()` in DuckDB's own `CAPIScalarFunction` (src/main/capi/scalar_function-c.cpp:202, v1.5.6), which runs before the C callback. The empirical test passed for the right reason but the comment named the wrong cause — the dangerous kind of wrong comment.
- 2026-10-09 ADR-0005 now has primary-source backing: the same C++ function ends `if (!function_info.success) { throw InvalidInputException(function_info.error); }` (scalar_function-c.cpp:210), so InvalidInputException for every error path is DuckDB's code, not an inference.
- 2026-10-09 `pyproject.toml` + `uv.lock` committed with zero runtime deps. `tools/gen_functions_doc.py` is stdlib-only, but AGENTS.md requires a committed lock; oracle deps land with tools/oracle/ in Gates 1-4.
- 2026-10-09 ADR-0002 rewritten to lead with the local three-platform WASM build rather than CI YAML reading, and to cite the six Rust community extensions that already ship WASM. The ADR had been understating its own evidence.
- 2026-10-09 `DEVIATION: corrected ADR-0006 scope — I overstated it.` Second investigation against execute_function.cpp (v1.5.6, lines 24-37): the dictionary optimization needs EXACTLY ONE non-constant argument. Every coordinate function takes both ra and dec, so `hpx_ang2pix(12, ra, dec)` is structurally ineligible. Six realistic sentinel-value catalogue shapes (Parquet and native, filtered) all returned the correct 19960 rows. The hazard is real only for single-column throwing functions fed a join-produced dictionary vector. Consequence: `healpix_strict_input=false` is demoted from "required mitigation" back to the README feature it always was; the strict default is no longer forced by this ADR. The exposed functions are Gate 1-2 (`hpx_parent`, `hpx_from_uniq`, `moc_from_json/ascii/fits`), noted in the ADR for design time.
- 2026-10-09 ADR-0007: `healpix_strict_input` stays `true` — maintainer decision. Rationale recorded: RA normalisation is sound (angle on a circle) but Dec clamping fabricates data at the pole; archive-grade consumer (adqlduck) prefers loud refusal over silent wrong answer. Option C (RA always normalised, Dec always strict, no setting) recorded as the preferred shape if the contract is ever reopened — it is a README change first.
- 2026-10-09 `CONTRIBUTING.md` added for the local build/test loop. Every command in it was executed in this session. README not edited (spec); a one-line link from README to CONTRIBUTING.md is for the maintainer to add.
